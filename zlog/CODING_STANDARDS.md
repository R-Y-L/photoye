# Photoye 工程开发规范与代码准则

> **生效版本:** 3.0  
> **适用范围:** Photoye 全仓库代码设计、编写、审查与重构

---

## 1. 变更控制与受控原则
- **优先代码复用**：实现新功能前，先全面通读已有模块（`models/`, `database.py`, `analyzer.py` 等），最大化复用现有类、工具函数与数据接口。
- **重大改动申报**：修改数据库核心表结构、重构底层推理流水线、变更现有公共 API 签名或增设核心模块前，先提交变更方案与改动点清单，经确认后实施。
- **精准交付**：仅编写需求规格直接规定的逻辑，保持代码库精炼纯粹。

## 2. 表达与注释规范
- **正向表达**：函数命名、条件分支与文档说明使用肯定语气。优先使用 `is_valid`、`is_ready`、`if enabled:`，保持逻辑清晰直观。
- **现行决策驱动**：注释与文档直接阐明当前技术方案的选型理由、业务逻辑与不变式，聚焦于现行代码的优势与预期行为。
- **风格一致性**：保持代码与所属模块现有的命名规范、类型注解与格式风格一致。

## 3. 架构与依赖原则
- **统一轻量运行时**：全栈依赖纯 Python 与 ONNX Runtime，保持各系统平台零外部编译、开箱即用。
- **全新设计，轻装上阵**：开发阶段直接采用 V3.0 最新定义的数据结构与接口，专注于当前业务闭环的高效实现。
- **分层解耦**：核心业务计算（AI 推理、分拣引擎、台账逻辑）与 PyQt6 界面表现层保持解耦，业务层提供独立自动化单测能力。

## 4. 阶段性提交与健康 Git 存档
- **健康存档**：阶段性小任务完成且验证通过后，立即停手并提供准确描述的 Git 提交提示词，经用户确认并提交后方可进入下一步，维持代码记录的完善与可回溯性。

## 5. 项目日志文件的创建与规划管理规范
项目文档统一集中维护在 `zlog/` 目录下，严禁在根目录散落临时说明文件。采用明确分工的“四权分立”文档体系：

### 5.1 文档体系职责与创建标准
1. **产品需求标准 (`zlog/REQUIREMENTS.md`)**：
   - **职责**：记录产品愿景、适用场景、痛点与功能规格说明（FRD）。
   - **维护准则**：属于业务需求原点，当产品功能定义发生变更时，由用户授权更新，保持业务目标明确。
2. **全局技术架构标准 (`zlog/ARCHITECTURE.md`)**：
   - **职责**：记录系统全局分层设计、目录职责、SQLite 数据库 Schema 权威定义、核心数据结构对象及核心算法公式。
   - **维护准则**：属于全工程的技术真理源与实现基准，代码编写与表结构扩展必须严格与此保持一致，保持长期稳定。
3. **全局开发路线图 (`zlog/ROADMAP.md`)**：
   - **职责**：以里程碑（Milestone 1~5）视角 100% 对应承接需求文档中的全部功能模块。
   - **维护准则**：记录各模块宏观交付项与验收指标，用于大方向对账与宏观进度掌控，杜绝功能遗漏。
4. **当前冲刺开发看板 (`zlog/DEVELOPMENT.md`)**：
   - **职责**：聚焦当前正在开发的具体阶段（Sprint），属于高频变动、记录细节的实时执行看板。
   - **维护准则**：包含当前具体任务清单、接口细节、单测断言与执行进展；随代码编写动态更新。

### 5.2 规划与流转边界准则
- **单向承接流动**：`REQUIREMENTS.md`（需求） $\to$ `ARCHITECTURE.md`（架构标准） $\to$ `ROADMAP.md`（全局规划） $\to$ `DEVELOPMENT.md`（当前冲刺）。
- **任务边界隔离**：严禁将未开发阶段的微观代码细节混杂堆砌在当前开发看板中，保持当前看板轻量清晰。
- **阶段流转闭环**：当前阶段的所有任务闭环并完成阶段性 Git 存档后，方可从全局路线图（ROADMAP）中提取下一个里程碑的任务载入当前冲刺看板（DEVELOPMENT）。
